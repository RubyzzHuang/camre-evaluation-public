ChatEHR
What evaluation looks like once the system is actually deployed

Full paper: "Adoption and Use of LLMs at an Academic Medical Center" · Shah, Ambers, Pandya, Keyes, Banda, Nallan, … Pfeffer · Stanford Medicine, Technology and Digital Solutions

Not a benchmark paper. This is a health system reporting 1.5 years of building, deploying and monitoring an LLM that reads the whole patient timeline inside the EHR — and reporting, with unusual candour, what its outputs actually get wrong in production. Its central claim for anyone building an evaluation plan: benchmark-based evaluation was insufficient once real users arrived, and new methods had to be built.

What was built

A platform, not a feature

In plain termsInstead of buying a vendor tool, the health system built its own layer that pulls a patient's entire record into an LLM's context in real time, inside the EHR. That layer then serves three different kinds of use: developers exploring, scheduled jobs doing rote work, and clinicians chatting with a chart.

Capability 1

Data orchestration

Extracts record elements by time range, encounter type, visit location and other attributes — defining exactly which slice of the record enters the context.

Capability 2

Context management

Combines the query with patient data in a token-efficient form. Most data is handled as FHIR; some content (referral records, transplant information) arrives in other formats and is processed natively.

Capability 3

LLM routing

Picks a model by token count, and splits context into chunks for parallel processing when it exceeds the window. Model-agnostic by design — the paper calls this critical for matching each task to the appropriate model.

Usage mode A

Exploration

Developers testing alternative uses against real-time data.

Usage mode B · 7 in routine use

Automations

Fixed prompt + code performing one task across many records — transfer eligibility, surgical-site-infection surveillance, referral extraction. The task is known in advance.

Usage mode C · ~100 daily users

Chat UI

A chat window embedded in the EHR; the user picks data sources and a time range, then asks anything. The task is not known in advance.

Timeline: sandbox April 2023 → conceptualised November 2023 → prototypes through mid-2024 → pilot early 2025 → 150 clinical users by August 2025 → health-system-wide rollout 9 September 2025 to roughly 7,000 physicians and advanced practice providers.

The organising idea — explore it

Evaluation strategy forks on one question: is the task known in advance?

This is the paper's most transferable contribution. The same three monitoring axes apply to both usage modes, but how each is measured changes completely depending on whether the task was known before deployment. Pick a mode to see the real metrics reported for each axis.

Note what the fork actually changes. For a known task a gold-standard truth set can be built up front — patient identifier, date range, prompt, clinician-adjudicated answer — and then reuse it forever as a regression test, including re-running it every time an underlying model is updated or deprecated. For an unknown task there is nothing to build a truth set against, so the paper reverse-engineers one: process the interaction logs, cluster what people actually asked into task categories, then build measurement for the tasks that turn out to be common.

The directly reusable method

How "unsupported claims" are counted

Descended from FactScore (break prose into atomic facts, check each against a knowledge source) and adapted from VeriFact. The implementation is published in enough detail to reimplement, including the prompts.

Retrieval setup
  • Segment both the generated summary and the underlying patient record into overlapping chunks — 500 characters with 50-character overlap.
  • Embed every chunk with a fixed embedding model (text-embedding-3-small).
  • For each summary chunk, retrieve up to 200 of the most cosine-similar source chunks from the record.
  • Adjudicate entailment with an LLM (Gemini 2.5 Pro).
Stage 1 · Entailment

Is each fact supported?

Returns a boolean plus a short rationale. The definitions are strict, and the third clause is the one that does the work:

  • Entailed — explicitly stated or unambiguously supported in the source.
  • Not entailed — missing, contradicted, or only inferable by external knowledge.
  • Stylistic differences are ignored; only factual content counts.

That third clause means a clinically reasonable inference the record does not actually state is counted as unsupported. This is a deliberately conservative bar.

→
Stage 2 · Classification + harm

What kind, and how bad?

Takes only the facts already marked non-entailed — it is explicitly forbidden from finding new ones — and sorts each into:

  • Hallucination — made-up information corresponding to nothing in the chart.
  • Inaccuracy — factually incorrect, contradicting the chart, or misrepresenting certainty (the paper's own example: "probable diagnosis" became "definite").

It then assigns the maximum harm the un-edited summary could cause if used for care:

1No harm
2Mild
3Moderate
4Severe
5Death

Worth flagging: the harm scale is fully specified in the published prompt, but no harm-level results appear anywhere in the paper. Every reported number is a raw count of unsupported claims, unweighted by severity. A summary with one potentially-lethal error and a summary with one trivial one are reported identically. The instrument to separate them was built and its output is not shown.

One more property worth noticing: "misrepresenting certainty" is classed as an inaccuracy. That folds a calibration failure — overstating how sure the record is — into the same counter as a wrong lab value, rather than tracking it as its own kind of error.

The movement is modest and mostly in inaccuracies (1.75 → 1.60); hallucinations were essentially flat (0.74 → 0.73). Half of production summaries still contain two or more unsupported claims. This is what a competently-run deployment looks like — an institution with governance, mandatory training and a responsible-AI lifecycle — which makes these numbers a more useful reference point than a benchmark score.

Four recurring error types, from manual review

The paper's own categorisation of what the errors mostly were:

1

Temporal sequence

Getting the order of events wrong.

2

Numeric confusion

Labs and vital signs mixed up.

3

Role attribution

Misstating who performed an action.

4

"Gestalt" care plans

Inferring the wrong overall intent — e.g. reading a pulmonary workup as a cardiovascular one.

Three of the four are failures of binding rather than of knowledge: attaching a real value to the wrong time, the wrong measurement, or the wrong actor. The paper names this directly in its limitations — "handling of time and attribution of facts" is listed as an unresolved technical challenge.

Before any of that scaled

Two pilots, wildly different outcomes

Both were summarisation automations. Both were built by the same team. The gap between them is the paper's clearest argument that task-and-workflow fit dominates model capability.

Pilot 1 · Otolaryngology pre-visit summary
⅔ usable

Summarised symptoms, medications, imaging and referral reasons from one year of notes, for 29 patients across 3 physicians over six weeks. 95.0% agreement with physician consensus.

Pilot 2 · Nursing shift summary
⅛ usable

Drafted a shift summary from flowsheets, medications and measurements. Evaluated by 6 nurses on correctness, completeness, conciseness and harm. Required significant context and prompt refinement.

A five-fold difference in usable output between two summarisation tasks at the same institution. The paper's reading is that both pilots "underscored the importance of having subject matter experts refine prompts in a close feedback loop within the clinical or operational workflow" — and that delivering output into the existing workflow, rather than beside it, was necessary for usage at all.

The repeatable process the pilots produced

Identify the workflow trigger → gather context data → standardise the prompt set → create a truth-set for evaluation in partnership with domain experts → deliver the output integrated into the user workflow → capture human-in-the-loop feedback → monitor.

Two of those seven steps are evaluation work, and one of them (the truth set) sits in the middle of the build rather than after it.

What real usage looks like

Adoption facts that complicate the usual metrics

Feedback is sparse and self-selected

Roughly 5% of users provide any feedback at all; of that, two-thirds positive and one-third negative. Any metric built on thumbs-up rates rests on a 5% sample that chose to respond.

Positive-feedback rate by medical task:

Summarise patient clinical history72.6%
Review oncology history74.2%
Review cardiology history80.0%
Generate MDT assessment notes91.7%
Identify barriers to discharge95.6%
The same task, phrased two ways, scores differently

"Summarize this patient's medical history" and "What is this patient's medical history?" are the same medical task but different language tasks. The satisfaction gap between the two phrasings:

Phrased as summarisation67.3%
Phrased as question-answering77.3%

A 10-point swing driven by how the user typed the request, not by what was being asked. Any satisfaction metric aggregated across free-form phrasing is measuring prompt style as much as system quality.

Task mix

849 medical task clusters found. Summary generation 30.3%, record review 27.6%. As language tasks: question-answering 42.3%, summarisation 30.6%. Ten of the twenty most common mapped onto the existing MedHELM taxonomy — and ten did not.

Interaction shape

75% single-turn, 25% multi-turn. The paper reads this as clinicians using it for retrieval and summarisation rather than collaborative reasoning.

Where the latency goes

Most queries return in under 20s; large records reach 50s. Two-thirds of that time is assembling the record, and for complex patients FHIR bundle assembly is over 95% of total time — not inference.

The categoriser itself was only partly validated. Two clinicians reviewing 100 sampled queries agreed with the model-assigned category 73.5% of the time for medical tasks and 69.5% for language tasks. Every task-stratified number above inherits that error rate — which is worth holding in mind before treating the per-task feedback rates as precise.

Putting a number on it

The value framework, and where it admits defeat

A finance-team-built framework with three benefit categories, applied at three lifecycle stages. First-year projections assume partial rollout and learning-curve effects; steady-state approximates year three.

Cost savings

Direct reductions in operational expense.

Time savings

Explicitly labelled "soft" — the time is repurposed, not eliminated.

Revenue growth

From new workflows, volume, throughput or margin.

The UI's own estimate, shown with its assumptions

~100 daily users × ~3 queries each × an assumed 10 minutes saved per query = 50 hours/day → at a $120/hour median physician salary → ≈$2.2M/year, against roughly $20,000/year in LLM costs. The paper is explicit that the 10-minute figure is an estimate and that no revenue growth is attributed to the chat interface at all.

The most honest passage in the paper is about why this is hard: saved minutes "often occur in fragments that cannot be used to perform other tasks." One automation avoids manual review of ~120 charts a day — about four hours of case-management time — which "do not translate directly into additional work completed." A separate case describes ChatEHR surfacing an outside diagnosis that changed a patient's pathology workup and produced a definitive diagnosis; the paper simply says the value of that better care is "near impossible to quantify."

What the authors flag as unresolved

Reading it with its scope attached

Verification behaviour may erode over time

The paper's sharpest forward-looking worry: as users grow used to AI-generated content, they may stop checking it. Its proposed response is a metric — monitor whether and how often users open the source documents, not just whether outputs are good. That is a usage signal standing in for a trust signal.

Time and attribution remain unsolved

Named directly as open technical challenges. Planned fixes: automatic citations linking each extracted fact to its exact location in the record, and UI guardrails that flag outputs with high uncertainty. Also in development: automated fact verification and synthetic truth-set generation.

Results are one institution's

Single academic medical centre plus a community hospital, with an established responsible-AI lifecycle, an embedded data-science team inside IT, and mandatory user training. The error rates should be read as achievable under those conditions, not as generic.

Equity of benefit is raised, not measured

The paper notes data disparities can produce performance gaps "even when demographic variables are not explicit inputs", and recommends monitoring performance across patient subgroups. No subgroup analysis is reported here.

Effective use depends on user skill

Query-writing and choosing the right data context both matter, and most users were new to generative AI. The 10-point phrasing effect above is this limitation showing up in the data. Mitigations used: a prompt library, "prompt-a-thons", a Teams channel, and a mandatory training video.

Feedback and sampling are thin in places

5% feedback rate; claim rates computed on a 10% session sample; task categorisation ~70–74% agreement with clinicians. None of this invalidates the findings, but the precision implied by two-decimal claim rates is greater than the measurement supports.
